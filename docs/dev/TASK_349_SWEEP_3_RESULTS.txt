FOUR CLASSES OF FAILURE, and only one of them is a matrix defect

1. ENVIRONMENT, not the arms and not the product -- G, H, I, J (4 arms)
     ValueError: --kv-session-offload-host-ram-gib=8 GiB does not fit in the
     currently available host RAM: 15.9 GiB available minus ...
   The box had ~15.9 GiB of host RAM free during the run. Decisive detail:
   B_offload carries the SAME flag and PASSED earlier in the same sweep, so
   the condition moved while the sweep ran -- something else on the box took
   the RAM (the 27 GB models-cache download is the obvious candidate). These
   four arms are not evidence about their crossings; they need a re-run on a
   quiet box before anything is concluded about offload x spec.

2. RUNTIME OOM, real findings for the next pass -- D and L (2 arms)
     D_offload_x_crossalgo: CUDA error: out of memory, at line 466 -- it
       BOOTED and died during serving, not at load.
     L_video_cotenancy: torch.OutOfMemoryError, GPU 0 (31.34 GiB) with
       63.69 MiB free, allocating 86 MiB.
   L is worth a note on the two device orders. Its budget 19000,15000,15000
   was accepted because the physical-impossibility guard reads NVML, where
   index 0 is a 3080 (20480 MiB) -- but at RUNTIME rank 0 is the 5090
   (31.34 GiB, torch order) and carries the double shard of the 2,1,1 ratio.
   The budget is legal and still wrong for the card the rank lands on. That is
   runbook 5.1 biting in a new place: the guard and the runtime disagree about
   which card rank 0 is.

3. ONE MORE COMPANION FLAG -- C_crossalgo
     --speculative-cross-algorithm-lazy-capture requires
     --speculative-cross-algorithm-... (next in the chain)
   The fourth layer on this arm. Each fix has revealed the next requirement,
   which is the normal shape for an arm that has never executed.

4. MARKER DRIFT, matrix-side -- reject_dcp_crossalgo
   The guard FIRED and it is the right one:
     "--draft-kv-layout dcp is not supported together with cross-algorithm
      speculative serving: the active draft rung changes at runtime, so the
      boot-time chain guarantee the DCP-sharded draft pool relies on does not
      hold."
   The arm expects the marker "--speculative-cross-algorithm", and that
   message names the feature in prose instead of by flag. So the arm reports
   FAIL for a boot that behaved correctly.

   THIS IS ALSO A LESSON ABOUT MY OWN PREP. Item 2 of the prep checked that
   every reject marker still appears in server_args.py -- and it does, because
   the flag is declared elsewhere in that file. "Present in the file" is not
   "present in THIS guard's message". The check should assert the marker
   against the specific message the arm's crossing produces, which is what the
   named-guard rule was supposed to mean in the first place.

PRODUCT BREAKS FOUND: none that this run can claim. The two OOMs are
configuration/budget findings on first-time crossings, the four RAM failures
are the box, and the marker drift is the net. No crossing produced a hang, a
silent misconfiguration, or an incoherent answer.
