Instrumente

Prefill tok/s (Rechenrate) = #new-token / compute-ms aus den Zeilen Prefill rank batch … gpu-ms: X (compute Y, wait Z), je Rang summiert über das Fenster; die Kachel zeigt den langsamsten Rang, denn eine PP-Stufe bzw. ein TP-Partner begrenzt jeden Chunk. Das ist Gerätezeit, also rechen-ehrlich: Leerlauf zwischen Anfragen senkt sie nicht.

Durchsatz Wandzeit = verarbeitete Prompt-Tokens im Fenster durch die Fensterlänge — das, was tatsächlich durchging, inklusive Leerlauf und Warten; ehrlich, aber keine Rechenrate.

input throughput aus der Zeile Prefill batch ist wall-konfundiert: es teilt durch die Scheduler-Wanduhr und springt bei Leerlauf. Es steht nur grau und unter diesem Namen da.

Decode tok/s = gen throughput der Zeile Decode batch (Tokens seit der vorigen Zeile durch die Zeit dazwischen); die große Zahl ist Tokens / Wanduhr: Σ(gen throughput × Zeilenabstand) / Σ Zeilenabstand, nie das Mittel der Raten. Prefill: die große Zahl ist Σ #new-token der ersten Stufe / Wanduhr der Prefill-Schübe (je Schub Start des ersten Chunks bis zur letzten Rang-Zeile; Leerlauf Wanduhr (Start des ersten Chunks bis zur letzten Rang-Zeile); die GPU-Rechenrategt; 5 s zwischen Schüben zählt nicht); die GPU-Rechenrate steht beschriftet daneben. Daneben die Rechenrate aus Decode rank batch: bs × accept len / gpu-ms je Runde.

Quelle sind die Boot-Logs, die der weg2-Launcher ohnehin schreibt (per Byte-Offset gelesen, nie ganz). Das Dashboard schickt keinem Modell eine Anfrage außer GET /weg2/state alle 10 s.
